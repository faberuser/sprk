# Database

The game database is PostgreSQL 18. This guide covers how the server uses it,
how to write SQL for it, how it is hosted and backed up, and how to diagnose a
slow, failing or locking game from the database and `sprk-game.log`.

## 1. Overview

- **Access.** sqlx 0.9 through `crate::db` (section 3). CI type-checks every
  literal SQL statement against the migrated schema with
  `server/scripts/database/check_sql.py` (a `PREPARE` sweep) instead of `query!` macros.
- **Schema.** `sqlx::migrate!()` files in `server/migrations/`, applied at startup with
  the owner role. `0001` holds the `sprk_*` helper functions, `0002`–`0007` the
  tables per area (core, progression, battle, community, services,
  compensation audit), `0008` the gameplay triggers and `0009` the
  response-cache revision triggers.
- **Roles.** `sprk_owner` owns the schema, runs migrations, backups and
  diagnostics. `sprk_app` is the game's role: data access only, not a
  superuser.
- **Pools.** The main pool and a read-only pool for `AppState.reads`
  (`database::init_database`, `open_read_pool`), each of
  `SPRK_DB_MAX_CONNECTIONS` connections (default 16, so up to 32 in all).
  PostgreSQL allows 100 in total, so keep it at 45 or below unless
  `max_connections` is raised. The read pool sets
  `default_transaction_read_only`, so a misrouted write fails instead of racing.
- **Session settings.** UTC, `statement_timeout` 30 s, `lock_timeout` 10 s,
  `idle_in_transaction_session_timeout` 60 s (role settings and pool options),
  so a stuck request never holds locks indefinitely.
- **Connection settings.** `DATABASE_URL` (app role) is required.
  `DATABASE_MIGRATION_URL` (owner role) applies migrations; without it
  `DATABASE_URL` is used. `DATABASE_READ_URL` optionally points the read pool
  elsewhere (a replica later).
- **Column types.** Integers are `bigint` (flags 0/1); JSON and timestamps are
  `text` (`YYYY-MM-DD HH:MM:SS`, UTC). Identity columns are
  `GENERATED BY DEFAULT`, so fixtures can keep explicit IDs.

## 2. Concurrency

Transactions run in parallel, so read-then-write code can lose updates or
deadlock unless it locks.

1. **Per-player serialization.** The `acting_account` middleware records the
   player of each POST request with a valid session; `database::begin` (used
   for every write transaction of a request) takes that player's
   `pg_advisory_xact_lock(account_id)`. One player's transactions run in turn;
   different players run in parallel. The lock lives in PostgreSQL, so it also
   holds across several `game` containers. It is held per transaction, not per
   request, so non-database work never blocks the player's other requests.
2. **Background, chat and battle work** has no acting account and takes
   explicit account locks (`postgres::lock_account`): co-op and arena
   settlement on the room master, mail, party messages, coupons, inventory
   initialization.
3. **Shared rows.**
   - Guild content: community requests of a guild member take the guild's
     lock (`postgres::lock_guild`) after the account lock.
   - Party/raid rooms: the room row is read `FOR UPDATE` before the JSON is
     rewritten.
   - Arena: matchmaking writes both players' queue entries and swords, so
     arena requests and arena settlements take one arena queue lock
     (`postgres::lock_arena_queue`) after the account lock and run in turn; a
     queue entry that changed anyway aborts the pairing.
   - Guild arena pairing locks the opponent guild with a `try` lock
     (skipping a busy one instead of waiting, which could deadlock) and
     re-reads it.
   - Counters shared across players (guild conquest keys, honor buff,
     friendship points) are single atomic statements.
4. **Retry wrapper.** `postgres::transaction(pool, Isolation, closure)` reruns
   on 40001/40P01. Request handlers do not use it (they have side effects
   inside transactions); a deadlock fails one request, which the client
   retries.
5. **Hot rows:** the global `('progression', 0)` revision (bumped by every
   world boss score and credential change) and per-guild rows during guild
   raids.

Lock waits of 250 ms or more are logged as `Waited long for a lock` with the
`lock`, `key`, `path` and `waited_ms`.

## 3. Writing SQL

All SQL is PostgreSQL with `$1, $2, …` placeholders. Helpers in
`server/migrations/0001_helpers.sql`:

| Need | Helper |
| --- | --- |
| Current or shifted time as text (UTC) | `sprk_datetime('now')`, `sprk_datetime(x, '-5 seconds')`; column default `sprk_now()` |
| Dates | `sprk_date(...)`, `sprk_utc_day()` |
| Epoch seconds of a text timestamp | `sprk_epoch(x)` (truncated) |
| Read a JSON field from a text column | `sprk_json_int` / `sprk_json_text` / `sprk_json_real` / `sprk_json` (jsonb), with `'$.a.b'` paths |
| Change JSON | `sprk_json_set` (one path; nest for several), `sprk_json_remove` |
| Inspect JSON | `sprk_json_type`, `sprk_json_array_length`, `sprk_json_each`, `sprk_json_ints($n)` (a JSON array of integers as rows) |

Helpers call each other schema-qualified (`public.`), because index
maintenance runs with `search_path = pg_catalog`.

Rules that do not show up as syntax errors:

- In `ON CONFLICT … DO UPDATE`, qualify the existing row: `SET n = t.n + excluded.n`
  (an unqualified `n` is ambiguous).
- `challenge_results."current_time"` must be quoted; unquoted it is the
  `CURRENT_TIME` function.
- `GROUP BY` is strict: group by the primary key to select other columns.
- `SUM(x)` returns `numeric`: write `SUM(x)::bigint`.
- `GREATEST`/`LEAST` ignore NULLs; `ORDER BY` puts NULLs last in ascending order.
- A failed statement aborts the transaction; use a savepoint (`tx.begin()`)
  to try something and continue.
- JSON fields compared in `WHERE` must use the same expression as their index
  (`sprk_json_int(data,'$.OnlineMatchUid')`, see `server/migrations/0004` and `0005`).
- `+account` in a `WHERE` clause keeps the planner off the account index on
  purpose (section 7).

### `crate::db`

`crate::db::query`, `query_scalar`, `query_as` and `RowExt::get`/`try_get`
replace their sqlx counterparts everywhere outside the database plumbing:

- **Binds:** every integer width and `bool` binds as `bigint`, JSON values as
  text. One parameter type per SQL text also avoids sqlx's prepared-statement
  cache error ("incorrect binary data format") when two call sites bind `i32`
  and `i64` to the same statement.
- **Decodes:** any integer column into any integer type (range-checked), into
  `bool` (non-zero) and `f64`; JSON text into `serde_json::Value`.

### Triggers and migrations

- Gameplay triggers are PL/pgSQL functions: progression metrics, play
  records, mail notifications, arena upkeep and retention (`0008`), and
  response-cache revisions (`0009`). Counters saturate at the `bigint` maximum
  instead of failing the gameplay write. Currency limits are `CHECK`
  constraints.
- `triggers_derive_the_recorded_rows` replays a fixed set of writes and
  compares every derived row with `server/tests/fixtures/trigger_rows.txt`. To change
  trigger output on purpose, rerun it with `SPRK_RECORD_TRIGGER_ROWS=1` and
  review the diff.
- Frequently updated tables use `fillfactor = 85`. JSON expression indexes:
  `arena_online_match_status`, `battle_state_dispatch_pending`.
- sqlx checksums migration files, and `.gitattributes` pins them to LF. Never
  edit an applied migration; add a new one. New migrations must stay
  compatible with the image still running during a deploy (add columns before
  use; drop later).

### Tests

`cargo test` needs `SPRK_TEST_POSTGRES_URL`, a role that may create databases
(see `README.md`). The first test builds a migrated template database; each
test clones it (`database::test_pool`). Helpers: `reconnect` (server restart),
`test_read_pool`, `row_changes` (rows written so far), `fail_trigger` (make
writes fail), `explain` (plans with sequential scans disabled). Concurrency is
covered by `account_lock_serializes_one_account_only`,
`request_transactions_serialize_per_acting_account`,
`acting_account_middleware_prevents_lost_updates_within_one_player`,
`transaction_retries_serialization_failures` and the concurrent claim and
purchase tests. CI runs the suite, the native Wine tests and the image smoke
test against PostgreSQL service containers, plus `check_sql.py`.

## 4. Hosting

`docker-compose.yml` runs `postgres` (volume `postgres-data`, no published
port, `pg_stat_statements` preloaded), `postgres-backup` and `game` (waits for
a healthy `postgres`). On first start of the volume, the init script
(`sprk-postgres-init` under `configs:`) creates the `sprk` database and the two
roles. The init and backup scripts are inline in the compose file because
Portainer git stacks cannot bind-mount files from the repository; this needs
Docker Compose 2.23.1 or newer. If the volume was created without them (roles
missing), run that script by hand in the `postgres` container.

| Variable | Use |
| --- | --- |
| `SPRK_DB_SUPERUSER_PASSWORD` | bootstrap superuser (maintenance only) |
| `SPRK_DB_OWNER_PASSWORD` | `sprk_owner` |
| `SPRK_DB_APP_PASSWORD` | `sprk_app` |
| `SPRK_DB_SHARED_BUFFERS` | about 25% of the memory available to PostgreSQL (default 512MB) |
| `SPRK_DB_MAX_WAL_SIZE` | default 4GB |
| `SPRK_DB_SYNCHRONOUS_COMMIT` | default `off`: a commit returns before its WAL flush (as the former SQLite `synchronous=NORMAL`). A host or PostgreSQL crash can lose the last ~0.6 s of commits but never corrupts. `on` waits for the disk on every commit (2–20 ms on the production disk). |
| `SPRK_DB_MAX_CONNECTIONS` | connections per pool (default 16) |

Use long random URL-safe passwords (letters, digits, `-` and `_`). They take
effect only when the volume is first created; change them later with
`ALTER ROLE … PASSWORD`. Add PgBouncer (transaction mode, 1.21 or later) only
for several `game` containers.

Locally, `start_server.bat` starts a loopback container (`sprk-postgres-local`,
port 54320, volume `sprk-postgres-local`) unless `DATABASE_URL` is set.

### Backups and restore

`postgres-backup` writes `sprk-<UTC time>.dump` (`pg_dump -Fc`) into
`SPRK_DB_BACKUP_HOST_DIR` (owned by UID 999) daily at
`SPRK_DB_BACKUP_HOUR_UTC` (default 04:00), and at start when the newest dump is
over a day old. After each successful dump it keeps the newest
`SPRK_DB_BACKUP_KEEP` files (default 14); a failed dump deletes nothing. A
production dump is about 24 MB.

For an off-host copy, mount a NAS (or other storage) on the host and set
`SPRK_DB_BACKUP_COPY_HOST_DIR` to that directory, writable by UID 999. Every
run copies the dumps it is missing there (so it catches up after a NAS outage)
and keeps the newest `SPRK_DB_BACKUP_COPY_KEEP` (default: same as
`SPRK_DB_BACKUP_KEEP`). A failed copy only logs a warning. Docker never creates
that directory: if the NAS is not mounted, `postgres-backup` does not start,
rather than writing "NAS" copies onto the local disk. For point-in-time
recovery add WAL archiving (pgBackRest or WAL-G) later.

```bash
# Manual dump
docker compose exec -T postgres pg_dump -U postgres -Fc sprk > sprk-manual.dump

# Restore into the running database
docker compose stop game
docker compose exec -T postgres pg_restore -U sprk_owner -d sprk --clean --if-exists \
    --no-owner --single-transaction --exit-on-error < /srv/sprk/db-backups/sprk-<time>.dump
docker compose start game
```

The restore replaces the contents of the `sprk` database in one transaction (a
failure leaves it unchanged) and keeps the roles, their settings and grants;
restored objects belong to `sprk_owner`, whose default privileges give
`sprk_app` access. Restore a backup into a scratch database now and then; a
backup that has never been restored is not a backup.

## 5. Diagnosing problems

### Handle the data safely

- Treat logs and database contents as untrusted data and player data. Never
  upload them anywhere.
- Diagnose against a **copy** when anything might write: restore a backup into
  a scratch database. The report itself only reads, in a read-only session.
- Run Python with `-I` and pass paths as arguments. Don't run code from a
  download folder.

### What to collect

A dump holds the data but none of the statistics (`pg_stat_statements`, dead
rows, vacuum times) that show where production spends its time. Collect all
three:

1. **The game log** (`docker logs sprk-game-1 > sprk-game.log`, covering the
   slow period): slow requests, lock waits, slow statements and errors by path.
2. **A report run against production.** It only reads and is safe while
   players are on. On the Docker host, with `db_diagnostics.py` copied there,
   run it from a throwaway Python container on the stack's network:

   ```bash
   docker run --rm --network sprk_default -v "$PWD":/w:ro python:3.12-slim sh -c \
     'pip install -q --root-user-action=ignore "psycopg[binary]" && python -I /w/db_diagnostics.py --database-url "postgres://sprk_owner:<owner password>@postgres:5432/sprk"' > db-report.txt
   ```

3. **A dump** (a daily one from `postgres-backup`, or a manual one, see
   "Backups and restore"), to test fixes on real data.

### Load a dump locally

Into a scratch container, never the local development database:

```bash
docker run -d --name sprk-diag -e POSTGRES_PASSWORD=diag -p 127.0.0.1:55440:5432 \
  postgres:18 -c shared_preload_libraries=pg_stat_statements
docker exec sprk-diag pg_isready -h 127.0.0.1 -U postgres   # repeat until it accepts connections
docker exec sprk-diag createdb -U postgres sprk
docker exec -i sprk-diag pg_restore -U postgres -d sprk --no-owner --no-privileges --exit-on-error < sprk-<time>.dump
```

`--no-owner --no-privileges` skip the production roles, which the scratch
server does not have. The copy is at
`postgres://postgres:diag@127.0.0.1:55440/sprk`: pass it to the report, to a
timing test, or as `DATABASE_URL` to a local server (its migrations are already
applied). Remove it with `docker rm -f sprk-diag` when done.

### Run the report

From the repository root (`pip install "psycopg[binary]"` for the database
part; connect as `sprk_owner`, which can read other sessions' activity and
`pg_stat_statements`):

```bash
python -I server/scripts/database/db_diagnostics.py --log <path/sprk-game.log> --database-url postgres://sprk_owner:...@host:5432/sprk
```

Either flag can be used alone. The report prints:

| Section | What it means |
| --- | --- |
| PostgreSQL contention errors | Deadlocks (40P01), serialization failures (40001), `lock_timeout`, `statement_timeout`, idle-in-transaction kills, too many connections, by path. A few deadlocks under heavy play are tolerable (the request fails and the client retries); a growing count names a hot row or an inconsistent lock order. |
| Pool acquire timeouts, slow acquires | All pooled connections were busy. Look for long transactions first, then raise `SPRK_DB_MAX_CONNECTIONS`. |
| `Waited long for a lock` | Waits of 250 ms or more for the same player's, a guild's or the arena queue's previous transaction, by lock and path. The holder is the slow path to fix. |
| `Slow HTTP request` by path | Requests of 100 ms or more (`SLOW_REQUEST_MS` in `performance.rs`). |
| sqlx `slow statement` | Single statements of 1 s or more, including lock waits. |
| Largest tables, dead rows, last vacuum | Growth and bloat. A table with many dead rows and no recent vacuum needs autovacuum tuning. |
| Buffer cache hit rate | Below about 99% under load means the working set does not fit in `shared_buffers`/memory. |
| Top statements (`pg_stat_statements`) | Where database time goes, by total time. Compare means before and after a fix. |
| Long transactions, lock waits | Live view: who holds locks others wait for. A transaction open for seconds usually awaits non-database work it should not hold a transaction across. |
| Plans of hot queries | Queries that run on a timer or hot paths. `Seq Scan` on a large table, or a `Filter` that parses JSON per row (`sprk_json...`), is a regression. |

### Rules when fixing

- Never `.await` non-database work (battle worker calls, network I/O, sleeps,
  heavy JSON building) inside a transaction: it holds the player's lock and
  any row locks for that long. Build what you can on the read pool first.
- A transaction that writes rows of **another** player or a shared entity
  must lock them: an atomic single statement (`UPDATE ... SET n = n + $1`),
  `SELECT ... FOR UPDATE`, or an advisory lock. Lock several entities in one
  fixed order, or use the `try` variants and skip a busy one, as guild arena
  pairing does. `crate::postgres::transaction` retries 40001/40P01 for code
  that can run twice.
- For a new periodic or hot query, check its plan on a copy (`EXPLAIN`) and
  add it to `WATCHED_QUERIES` in the report script.
- Name long-running background tasks with `database::spawn_labelled`
  (`task:dispatch-preparation`, `task:battle-connection`, …) so their logs and
  lock waits say where they come from.
- Server-only changes need no client release (see `AGENTS.md`). Run
  `cargo test` and `check_sql.py`, then report before/after numbers.

### Measuring a request or startup on real data

- Restore a backup into a scratch database. To time a handler, write a
  temporary `#[ignore]` test that connects with `crate::postgres::connect_read`
  or `connect`, loads `GameTables` from `tables`, and calls the handler.
  `SPRK_PROFILE_DATABASE_URL` drives the existing `profile_snapshot` harness.
  Install a `tracing_subscriber` with the filter `sqlx::query=debug` for
  statement times.
- Startup on the release binary in a scratch folder:
  `DATABASE_URL=<scratch db> RUST_LOG=info PORT=18080 GAME_TABLES_PATH=<repo>/tables target/release/sprk-server.exe`.
  `GameTables::load` dominates (about 25–40 s of JSON parsing, not the
  database); migrations and startup recovery take under a second.

## 6. Capacity

- Target: about 2000 players, so 200–500 online and about 20–100 database
  requests/s at peak. A single write's latency is set by the commit (WAL
  flush to disk), not CPU, so fast local storage matters more than cores.
  Watch lock waits and the top statements as load grows.
- There is a single `game` process. Dispatch preparation admits up to four
  simulations at once on the battle worker (`CONCURRENCY` in
  `cooperative_dispatch.rs`). Each pending job has its own task that takes a
  slot, prepares one repeat, saves it and queues again; slots are
  first-in-first-out, so jobs take turns and a long fight holds only its own
  slot. A scan every 3 s starts tasks for new jobs.
- Only the first `SAMPLE_FIGHTS` (20) fights of a dispatch are simulated
  natively; the rest are drawn from those samples as whole (outcome, time)
  pairs, seeded from `SimulationJobId`. The job then stores `SampledFights`,
  leaves the preparation queue and gets a fixed deadline. Rounds are revealed
  by the usual clock, and rewards follow the final win count. A job is behind
  when its prepared simulated fight time is less than the real time since it
  started; its round counter then stalls. Measure queue delay and CPU before
  raising the concurrency.

## 7. Design notes on hot paths

- **Arena rows** are large: Honor (BanPick) registers the whole collection, so
  an `arena_runs` row can reach 1.2–1.8 MB.
  - Each registered `AccountInfo` lives in `arena_snapshots(run, data)`,
    written once at registration (`Register.AccountInfo` is null in the run
    JSON; an `AFTER DELETE` trigger drops it with the run). Pairing stores
    Honor's `Wait.MatchInfo.AccountInfos` as `[]` and re-polls rebuild it
    (`arena::stored_wait`), so polls, pairing, triggers and settlement handle
    a few KB. `arena::prebuild` builds the registration's Hero snapshots on
    the read pool before any lock is taken. Readers of old inline rows keep
    working (`arena::registered_account`, `COALESCE` in ranking decks and
    Honor season records).
  - Queue polls update only `arena_runs.last_poll`; pairing filters on the
    `last_poll` and `season` columns (index `arena_waiting_queue`).
    `last_poll` is excluded from the progression revision triggers.
  - Account-scoped `OnlineMatchUid` lookups write `+account` so the planner
    uses `arena_online_match_status` instead of the account index, which
    would JSON-parse every run of that player; the match result lookup
    selects ids through a `UNION` so the JSON is only read through that
    index. `arena_completion_lookup_uses_match_index` checks the plans.
  - Settlement writes `MatchUid`/`GiveUp` with the result in one update and
    drops the completed row's `Wait.MatchInfo.AccountInfos`.
  - Rankings (`battle_info_kind`, `get_match_rank`, inspection, season
    rewards) count the rows ahead of one account (`ranked`) instead of
    building the whole leaderboard; world rankers build only the requested
    page. Ranking decks filter on the trigger-kept `season`/`squad` columns.
  - Retention: each player keeps only the newest `ARENA_RUNS_KEPT` (20)
    finished runs per arena kind, plus the newest complete run per season, the
    newest squad run per season and the newest non-friendly run. The
    `arena_retention_*` triggers prune inside the statement that finishes a
    run, first folding deleted runs into `arena_history_archive` (per account,
    kind and UTC day), which mission history adds back.
- **Mail.** `mails` rows reach about 0.2 MB; watch the table in the
  largest-tables section. Rewards that overflow a full bag join the batch's
  open mail, up to `OVERFLOW_MAIL_EQUIPMENT` (25) pieces; `item::free_slots`
  counts once per grant, and a batch that fills the bag stops counting.
  Claiming a mail needs room for all of its pieces.
- **Hero snapshots** (`community::cached_hero`) fetch all ten equipped pieces
  in one statement. A whole-roster Hero preset writes one row per changed Hero;
  batch `break_equip` clears references once and grants summed materials once
  per item.
- **Read pool.** `inspect_user` and the `sync_seen_categories` category check
  (`View::load`) run on the read pool; the main pool only records the seen
  categories.
- **Unimplemented endpoints** log their method, path and field names only,
  never values (they carry live `SessionKey`s).

## 8. Later

- **Tuning.** Hot JSON fields to columns or `jsonb`, text timestamps to
  `timestamptz`, 0/1 flags to `boolean`, batching hot counters, autovacuum settings. Measure first
  with the report.
- **Compatibility layer.** `crate::db`'s lenient binds and decodes are needed
  while columns are `bigint` and Rust fields are `i32`/`u8`/`bool`; it shrinks
  as columns get native types. The `sprk_json_*` helpers stay while JSON is
  `text`, and the time helpers while timestamps are `text`. Never drop a
  helper that an index, trigger or older migration uses; add a new migration
  instead.
- **Several `game` containers.** The database locks already work across
  containers; in-process state does not: sessions, chat, co-op/battle rooms and
  the Wine battle worker. Options: sticky routing so a room lives on one
  instance, plus Valkey/Redis for sessions and pub/sub. Add PgBouncer then.
- **AWS.** RDS or Aurora PostgreSQL needs only new URLs, RDS Proxy as the
  pooler and `DATABASE_READ_URL` pointing at a reader. Distributed PostgreSQL
  (Aurora DSQL and others) needs the retry wrapper on request transactions and
  a check of its feature limits (advisory locks, triggers) against the schema.
